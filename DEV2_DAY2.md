## Принятые правила

Значения — ммоль/л, скорость — ммоль/л в минуту, время — datetime с часовым поясом. Внутри время приводится к UTC.

| kind | Условие | Текущий уровень |
|---|---|---|
| low | Последнее значение < 3.9 и >= 3.0 | important |
| very_low | Последнее значение < 3.0 | critical |
| fast_drop | `Forecast.rate < -0.17` | important |
| fast_rise | `Forecast.rate > 0.17` | standard |
| high_1h | Все показания непрерывного участка > 10.0, участок >= 60 мин | important |
| very_high_1h | Все показания непрерывного участка > 13.9, участок >= 60 мин | critical |
| no_data | Возраст последнего показания >= 20 мин | important |
| no_data | Возраст >= 30 мин и последнее значение < 3.9 | critical |

Уровни для `no_data` заданы финальным TODO. Уровни остальных правил в доступном файле не определены явно: таблица — предварительное решение для проверки командой, менять его нужно в `config.LEVELS`. Это реализация настроек учебного проекта, не медицинские рекомендации.

Сравнения по значению и скорости строгие: 3.0 относится к low, 3.9 — уже не low, скорость ровно 0.17 не вызывает fast_rise. Для часа выбрано включение ровно на 60-й минуте. Максимальный промежуток между показаниями — 10 минут; больший разрыв обрывает непрерывный участок. Эти граничные соглашения нужно сверить с планом v2 и `facts`.

`very_low` заменяет `low`, `very_high_1h` заменяет `high_1h`, когда обе длительности достигнуты. Быстрое падение может сосуществовать с low/very_low. Уведомления о высоком значении сразу после одного показания не создаются: в среду требуются именно часовые правила.

При возрасте показания от 20 минут возвращается только no_data. Так старое значение или старый Forecast не выдаются за новое текущее событие. `Alert.value` у no_data содержит последнее известное значение; текст бота должен явно это обозначать.

Если история пуста, возвращается пустой список: из этих аргументов неизвестно, сколько времени пользователь уже ждёт первый замер. Для контроля первого подключения платформе понадобится время начала мониторинга. Будущие показания не используются. Одинаковые дубликаты удаляются, противоречащие показания одного времени вызывают ValueError. Некорректные значения и время без часового пояса тоже вызывают ValueError.

## Подключение к проекту

1. Создай feature-ветку по инструкции ниже.
2. Распакуй архив отдельно и перенеси его содержимое в корень клонированного `diabetrics` — туда, где лежит основной README проекта. Должно получиться `diabetrics/app/alerts/engine.py`, без лишнего вложения `diabetrics/dev2_day2/`.
3. Если эти файлы уже есть, сопоставь содержимое перед заменой: архив нельзя слепо накладывать поверх работы коллег. Общие `app/models.py`, README, зависимости и `.gitignore` здесь не заменяются.
4. Если каркас ещё не готов, временные модели позволяют тестировать отдельно. В проекте используется Python 3.10+; точную командную версию уточни по его конфигурации.
5. Когда появятся модели тимлида, сверить поля и заменить определения в `app/alerts/contracts.py` импортами из `app.models`. При совпадении полей это одно место импорта; при отличиях нужен явный адаптер, а не простая замена строки вслепую.

Временные поля:

```python
Reading(ts: datetime, value: float)
Forecast(rate: float, value_20: float | None = None, value_30: float | None = None)
Alert(kind: str, level: AlertLevel, value: float, ts: datetime)
```

Временные модели не включают ID пользователя, ID уведомления, статус подтверждения или хранение. Это ответственность общего контракта и платформы. Сейчас Alert.ts — время оценки, Alert.value — последнее измеренное значение. До интеграции команда должна подтвердить эти соглашения.

Пример:

```python
from datetime import datetime, timezone
from app.alerts import evaluate
from app.alerts.contracts import Forecast, Reading

now = datetime(2026, 11, 11, 12, tzinfo=timezone.utc)
history = [Reading(ts=now, value=3.5)]
alerts = evaluate(history, Forecast(rate=-0.2), "normal", now, [])
print([(a.kind, a.level.value, a.value) for a in alerts])
# [('low', 'important', 3.5), ('fast_drop', 'important', 3.5)]
```

Dev1 передаёт очищенную историю и `now` из `app.clock.now()`, включая demo-clock. Dev4 передаёт Forecast с rate за 15 минут, относящийся к последнему показанию этой истории. При отсутствии надёжного прогноза передаётся None; низкие значения и no_data всё равно обрабатываются.

Платформа должна вызывать evaluate по часам даже без нового показания: иначе no_data никогда не сработает. Запрет повторной обработки измерения не должен останавливать эту проверку времени.

`mode` и `recent_alerts` приняты для нужной сигнатуры, но в день 2 не меняют результат. Режимы запланированы на четверг, антиспам — на пятницу. Повторный одинаковый вызов даёт те же совпадения правил. Вызов evaluate сам по себе не означает «отправить все сообщения снова»: дедупликация и эскалация подключаются на следующих этапах. Не подключать этот модуль к непрерывной рассылке до реализации этих пунктов.

## Как проверить локально

Открой терминал **в корне проекта**. Быстрая проверка без установки дополнительных библиотек:

Для pytest создай отдельное окружение, если в проекте ещё нет своего. Команды ниже — для PowerShell в Windows:

Ожидается 34 успешных теста. Установи также общие зависимости проекта, если существующий `app/__init__.py` их импортирует. В `.venv` не надо выполнять git add.

## Как отправить в GitHub самому

Ни push, ни commit, ни PR, ни merge от твоего имени не выполнялись.

### 1. Скачать проект и создать ветку

Если проект ещё не клонирован:

```bash
git clone git@github.com:diabetrics-team/diabetrics.git
cd diabetrics
```

Если уже скачан, открой терминал внутри существующей папки. Второй clone не нужен. Проверь локальные изменения и удалённые ветки:

```bash
git status
git fetch origin
git branch -r
```

Если git status показывает твою незавершённую работу, сначала сохрани её в её ветке. Не выполняй reset --hard для очистки.

**В твоей памятке основная рабочая ветка — develop, в TODO — dev.** Посмотри вывод git branch -r и уточнение тимлида. Дальше приведён твой вариант с develop. Если команда действительно работает в dev, замени develop на dev и в командах, и в base у PR. Если есть обе ветки, само их наличие не говорит, какая нужна: следуй правилу тимлида.

```bash
git switch develop
git pull --ff-only origin develop
git switch -c feature/dev2-alerts-day2
```

Если develop существует только на сервере, вместо первого switch:

```bash
git switch --track origin/develop
```

`--ff-only` останавливается при расхождении истории, чтобы не создавать неожиданный merge. В таком случае нужно разобраться с сообщением Git, а не делать принудительный reset.

### 2. Перенести файлы, проверить и закоммитить

Скопируй файлы из архива по инструкции выше. Затем запусти тесты. Из корня проекта:

```bash
python -m unittest discover -s tests -p "test_dev2*.py" -v
git status
git diff -- app/alerts tests/test_dev2_rules.py requirements-dev2-dev.txt DEV2_DAY2.md
git add app/alerts/__init__.py app/alerts/config.py app/alerts/contracts.py app/alerts/engine.py tests/test_dev2_rules.py requirements-dev2-dev.txt DEV2_DAY2.md
git diff --cached --stat
git diff --cached
git commit -m "feat(alerts): implement dev2 day 2 evaluation rules"
```

`git diff` до add не показывает новые untracked-файлы; после add они видны в `git diff --cached`. Просмотри его полностью. В staged должны попасть только твои перечисленные файлы, без `.env`, токенов, виртуального окружения и чужих изменений. Если до начала там уже были staged-файлы, разбери их до commit.

В исходной памятке не хватало **git add и git commit**. Push отправляет коммиты; несохранённые в коммит изменения он не отправит.

### 3. Отправить ветку

```bash
git push -u origin feature/dev2-alerts-day2
```

`-u` связывает локальную ветку с удалённой. После следующих правок в этой же ветке достаточно:

```bash
git add app/alerts/__init__.py app/alerts/config.py app/alerts/contracts.py app/alerts/engine.py tests/test_dev2_rules.py requirements-dev2-dev.txt DEV2_DAY2.md
git diff --cached
git commit -m "fix(alerts): address review feedback"
git push
```

Если SSH отвечает `Permission denied (publickey)`, нужно настроить SSH-ключ именно в среде, где выполняется git, или использовать доступный команде HTTPS-доступ. Windows и WSL могут иметь разные SSH-настройки. Не отправляй никому приватный ключ и не вставляй токены в команду или README.

### 4. Создать PR

Открой https://github.com/diabetrics-team/diabetrics и нажми **Compare & pull request**. Если жёлтой плашки нет: **Pull requests → New pull request**.

- base: **develop** (или подтверждённая командой dev);
- compare: **feature/dev2-alerts-day2**;
- заголовок: `feat(alerts): правила Dev2 за день 2`;
- Reviewer: выбери тимлида или другого участника команды, который проверит код.

Рекомендуемый текст описания PR:

```text
Реализованы правила low/very_low, fast_drop/fast_rise из Forecast.rate,
high_1h/very_high_1h и no_data по TODO дня 2.
evaluate работает без БД и Telegram; пороги вынесены в config.py.

Проверка: 34 теста прошли через unittest.
Тесты включают граничные значения, непрерывность истории и синтетические
последовательности normal/night_hypo/fast_drop/hyper_long.

До готовности к интеграции:
- сверить временные модели с контрактами v2 и заменить их импортами/адаптером;
- подтвердить предварительные уровни и границы из DEV2_DAY2.md;
- добавить и прогнать проверки по официальным scenarios.json facts и fake_cgm/data.
Официальные fixtures недоступны в этой поставке, их прохождение не заявляется.

Режимы, эскалация и антиспам остаются задачами следующих дней.
```

Пока три пункта сверки не закрыты, создай **Draft pull request**. Это даёт команде возможность посмотреть код, не заявляя готовность к merge. Когда сверка пройдёт, нажми Ready for review. Ревьювер проверяет PR и ставит Approve. Замечания исправляются коммитами в той же ветке — новый PR не нужен.

После успешных проверок и одобрения участник с правами нажимает **Squash and merge → Confirm squash and merge**, затем **Delete branch**. Самостоятельно обходить проверки или сливать до согласования не нужно.

### 5. После merge

```bash
git switch develop
git pull --ff-only origin develop
git fetch --prune
```

После squash локальная feature-ветка может не удалиться через `git branch -d`, потому что её исходные коммиты не вошли в develop напрямую. Её можно оставить. Удалять локальную копию стоит только после проверки, что PR смержен и все нужные изменения есть в develop.
